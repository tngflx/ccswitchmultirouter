## 2026-08-30 - Selective upstream exit-recovery port and orphan cleanup

- **What happened:** The BigStrongSun `ccswitchmulti` PR #73 addressed a related recovery symptom: normal exits could be classified as unclean and takeover backups could be lost. - **What we did:** Ported `CleanExit` classification and macOS `proc_pidpath`/`proc_pidinfo` identity handling manually. Adapted clean-backup preservation/rebuild into the current OAuth-aware proxy service, removed the obsolete narrow restore helper, and rejected malformed or proxy-placeholder backups as preservation sources. Retained our independent Windows backup cleanup, terminal quota detection, per-attempt outcome suppression, and authenticated polling shutdown.

## 2026-08-30 - Dev rebuilds now hand proxy listeners over before relaunch

- **What happened:** A delayed `pnpm dev` rebuild could leave the replacement CCSwitch generation unable to restore Codex takeover while Codex Desktop remained open. Startup retried port `15721` twelve times, reported `PORT_OWNERSHIP_GUARD`/Windows error 10048, and only recovered after the old socket state eventually cleared or takeover was toggled manually.
- **Root cause:** The development launcher identified the correct Cargo-owned `cc-switch.exe` but always terminated it with `taskkill /F`. That bypassed `ExitRequested -> cleanup_before_exit()`, recorded every rebuild as an unclean exit, and started the replacement after WMI reported process disappearance without proving the old listener endpoint was bindable again. A plain non-forced close was also insufficient because the application intentionally converts ordinary close requests into hide-to-tray.
- **What we did:** Added a debug-only, per-launch random-token shutdown marker. Immediately before a verified non-forced close request, the launcher arms the marker; the app consumes it in `CloseRequested`, calls `app.exit(0)`, and therefore runs the existing proxy stop/Live-config restore path while preserving the persisted takeover switch. The launcher retains a PID-identity-checked forced fallback, never traverses through Codex descendants, captures every TCP listener owned by the verified app, and blocks the next generation until it can bind and release each captured endpoint itself.
- **Evidence:** `node --check` passed for both launcher files; `node --test scripts/dev-tauri-delayed.test.mjs` passed **36/36**; script Prettier and scoped `git diff --check` passed; `cargo test --manifest-path src-tauri/Cargo.toml dev_shutdown_marker_requires_the_exact_token_and_is_consumed --lib` passed **1/1**; `cargo check --manifest-path src-tauri/Cargo.toml` passed. Repository-wide `cargo fmt --check` remains red on pre-existing formatting drift in other dirty files. The already-running launcher loaded the previous JavaScript implementation, so the new end-to-end graceful handoff has not yet been live-tested; no user-owned `cc-switch.exe` or Codex process was manually terminated.
- **What NOT to do again:** Do not equate process disappearance with listener reusability, do not use `/F` as the normal dev-rebuild path, do not rely on an ordinary window close when close-to-tray is enabled, and do not “fix” this lifecycle race by only increasing startup takeover retries.

## 2026-08-30 - Correction: dev rebuilds require a build-input content baseline

- **What happened:** The delayed Tauri launcher still rebuilt the backend 50 seconds after the first successful launch even though no watched backend file had a final `LastWriteTime` during that interval.
- **Root cause:** The earlier watcher fix filtered raw events by file metadata without first recording what the successful build actually contained. The first event for any regular file was therefore still classified as a change, same-size rewrites were ambiguous, and deletion events were discarded. The rebuild gate also had no way to cancel a pending rebuild when edited contents returned to the build baseline.
- **What we did:** Replaced the metadata filter with a SHA-256 snapshot of all watched backend inputs. Batched watcher events now reconcile final file contents against the current build baseline, ignore unchanged files and transient paths, detect additions/deletions, avoid extending the quiet period for duplicate notifications, and cancel the queued rebuild when contents revert. The watcher is armed before the initial baseline is captured so real edits during the first Cargo build still queue exactly one follow-up build.
- **Evidence:** `node --check scripts/dev-tauri-delayed.mjs` passed; `node --test scripts/dev-tauri-delayed.test.mjs` passed **32/32**, including the exact first-launch/no-second-build regression and deletion coverage; script-only Prettier and scoped `git diff --check` passed; `pnpm dev -- --help` loaded the corrected default wrapper. A live first-launch restart was not run because active user-owned `cc-switch.exe` development processes remained running and rule 21 forbids terminating them without explicit permission.
- **What NOT to do again:** Do not infer a source edit from the first `fs.watch` event or from size/mtime alone; compare final contents with the inputs of the running build, and preserve deletion plus edit-revert semantics.

## 2026-08-30 - Startup log storm traced to rollout identity and idle-parent assumptions

- **What happened:** Startup emitted 118 Codex usage-sync warnings that forked rollout filename IDs disagreed with `session_meta.id`, 24 warnings that parent rollouts had not reached the child fork time, and repeated proxy-port recovery warnings during development restarts.
- **Root cause:** Codex uses a valid two-UUID filename form for forked task files: the first UUID is the root metadata ID and the trailing UUID is the actual child thread ID. The importer compared only the trailing UUID to root metadata and rejected valid files. It also incorrectly required a parent rollout to contain an event at or after the child fork timestamp, although an idle or archived parent may legitimately have no event near the later fork. Separately, raw `fs.watch` directory/unchanged events could be treated as backend source edits by the delayed development launcher and schedule an unnecessary second Tauri generation.
- **What we did:** Parsed forked rollout filenames as separate root-metadata and child-thread identities, retained the child ID for usage request identity, and accepted a complete readable parent token timeline even when its last event predates the fork. Added regression tests for both cases. Tightened the development watch path with regular-file content signatures so directory and unchanged events cannot schedule a rebuild. Added `AGENTS.md` rule 6-A requiring fixes at the invariant-owning layer and explicitly labeling unavoidable containment.
- **Evidence:** `services::session_usage_codex::tests::` passed **47 tests, 0 failed, 1 ignored**; both new regression tests passed individually **1/1**; delayed-launcher Node tests passed **27/27**; recovery-outcome tests passed **7/7**; `cargo check --manifest-path src-tauri/Cargo.toml` passed; scoped `git diff --check` passed. A live restart was not forced because a running `cc-switch.exe` was in use and rule 21 forbids terminating it without explicit permission.
- **Don't again:** do not assume every rollout filename contains only one semantic UUID, do not require an idle parent to emit at the exact fork boundary, do not treat raw filesystem watcher noise as proof of a source edit, and do not silence these warnings while leaving the importer or launcher invariant wrong.
