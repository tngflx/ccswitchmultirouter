## 2026-09-02 - Guardian v2 recurrence came from an unpinned Desktop/app-server schema boundary

- **What happened:** The `FeatureToml in features.guardianv2` resume failure returned after the earlier backup/write-boundary fixes, often only after Codex Desktop had been open for a while.
- **Root cause:** The earlier fix normalized a structured Guardian v2 value only when CCSwitchMulti happened to write `config.toml`. When the key was absent, Desktop package `26.831.1445.0` could later initialize the under-development feature as a structured table, while the installed `codex-cli 0.150.1` app-server expected the shared feature value to remain a scalar. Recovery replay amplified the problem but was not the original producer.
- **What we did:** Added a lifecycle compatibility invariant that pins `features.guardianv2 = false` when missing and repairs later structured rewrites through the existing locked atomic reconcile path. The Codex guardian checks that invariant while takeover is active. The official disable command confirmed the effective default but removed the explicit false value, so the current live installation was pinned through the same new atomic reconcile boundary.
- **Evidence:** `codex features list` identifies `guardianv2` as `under development` and reports `false`; the official disable command left the key absent, proving an effective default was not a durable schema pin; the one-off live reconcile wrote the explicit scalar without stopping Codex or CCSwitchMulti. Focused Guardian tests passed **4/4**, including missing-key pinning, simulated Desktop structured rewrite, backup recovery, and idempotence; Codex guardian tests passed **3/3**; `cargo check --manifest-path src-tauri/Cargo.toml` passed; scoped `git diff --check` passed.
- **What NOT to do again:** Do not treat recovery normalization as sufficient when an external process can recreate an incompatible schema after startup. Keep the compatibility scalar present for the full Desktop lifecycle, and do not repair the live Codex file through a raw writer.

## 2026-09-02 - Oversized compaction loop root cause confirmed and history replay bounded

- **What happened:** The September 2 live log showed an oversized Sublyx Codex turn reaching 1,001,804 bytes, followed by CCSwitch scheduling `oversized_compaction` and submitting a second 958,366-byte compaction request. A separate audit found the Responses-to-Chat history bridge could prepend a cached exchange even when the client had already supplied context.
- **Root cause:** Request Health treated a byte heuristic as permission to create a native compaction turn, but it did not own a continuation boundary; the resulting compaction request re-entered the same oversized path. Independently, `CodexChatHistoryStore::enrich_request` replayed cached semantic history whenever no tool output was present, including ordinary context-bearing requests, allowing duplicate history growth for Chat-compatible providers.
- **What we did:** Removed the oversized auto-compaction scheduler and its Desktop submission path (the existing bounded stream-recovery continuation remains). Restricted cached exchange restoration to context-free tool-output shorthand and added a regression proving a client-supplied next message is not prefixed with the cached exchange.
- **Evidence:** Historical router log lines at `09:45:59` show `oversized_compaction status=scheduled`, `status=submitted`, then `codex_request_kind=compaction` with `request_bytes=958366`; current source contains no `oversized_compaction` scheduling symbol. `cargo test --manifest-path src-tauri/Cargo.toml --lib proxy::providers::codex_chat_history::tests -- --nocapture` passed **10/10**.
- **What NOT to do again:** Do not let a diagnostic byte threshold create a compaction or continuation request. Do not restore cached semantic exchanges when the client already supplied context; only repair the minimal context-free tool-output form.
